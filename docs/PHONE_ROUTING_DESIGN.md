# 사건별 전화 연락 대상

상태: 사용자 요청으로 구현 반영. 최신 명칭 정정은 **사내 119**다. 모든 역할의 실제 시연 수신번호는 기존 비공개 설정의 번호 하나를 유지한다. 자동 발신 설정도 기존 꺼짐을 유지했다.

## 연락 정책

| 사건 | 기본 연락 역할 | 선택 방식 |
| --- | --- | --- |
| `VIOLATION_SUSPECTED` 미착용 | 현장 안전관리자 | Decisions 추천 + 고정 정책 검증 |
| `PRODUCT_MISMATCH_SUSPECTED` 보호복 불일치 | 현장 안전관리자 | Decisions 추천 + 고정 정책 검증 |
| `RELEASE_SUSPECTED` 누출 의심 | 안전 관제실 | Decisions 추천 + 고정 정책 검증 |
| 담당자가 사내 119 선택 | 사내 119 | 변경 사유를 기록한 수동 시연 |

사내 119의 자동 조건은 미정이다. 기존 사건 severity와 PPE/제품 판정은 변경하지 않는다. 화면·음성은 사내 119로 통일했고 과거 계획/API 호환용 역할 키 `external_119`는 유지한다. 이 키를 실제 전화번호 119로 해석하는 경로는 없다.

## 구현 흐름

`event → ContactRouter → contact_decision → notification_plan → phone_call → OpenAI Realtime`

- `chemiguard/contact_routing.py`는 별도 `gpt-6-luna` Decisions 요청을 공식 OpenAI 주소로 보낸다. 기존 PPE/제품 요청과 분리된 연락 추천 worker를 사용한다.
- 입력은 저장 사건의 종류·시각·개소·근거 관찰과 구조화된 결과다. 번호·키·원본 영상·사진·자유 서술 지시는 입력에 포함하지 않는다. 제품 전용 observation과 부모 PPE의 유효성도 검사한다.
- `contact_role`, `evidence_state`, `reason_code`를 choice로 요청한다. 실제 답·확률 분포·입력 snapshot/hash·모델·버전·지연을 남긴다. 점수를 현장 안전 확률로 표시하지 않는다.
- 오류·거절·형식 오류·정책 불일치에서는 이미 유효한 세 종류 사건에 한해 고정 연락 규칙을 적용하고 `policy_fallback`으로 기록한다. 모델이 119를 추천해도 자동 연결하지 않는다. 근거 누락·폐기·오류·다른 run·검토된 사건은 제외한다.
- 동일 사건·정책·프롬프트 버전은 한 번 호출하고 이후 캐시를 사용한다. 네트워크 요청 전체 상한은 3초, 연락 대기열은 8건이다. 중단된 요청도 자동 재시도하지 않는다.
- `notification_plan`은 역할·선택 주체·변경 사유·revision·시연 재생 여부를 남기는 추가 기록이다. 담당자 선택이 기존 AI 결과를 덮어쓰지 않는다.

자동 발신이 꺼져 있어도 준비된 서버는 이후 생성되는 유효한 사건의 연락 추천을 만든다. 실제 발신은 담당자 확인 후 진행한다. 자동 발신이 켜진 경우 새 사건에 기본 정책을 적용하되 담당자가 만든 계획을 자동 119 전화 등으로 승격하지 않는다. 재시작 때 과거 사건을 발신하거나 추천 대기열로 재생하지 않는다.

## 화면과 API

전화 알림 페이지 또는 사건 상세의 ‘사건 연락 대상’에서 AI 추천과 적용 정책을 확인한다. 세 역할 중 선택하고 다른 역할이면 사유를 입력한 뒤 선택을 저장한다. 120초가 지난 사건의 수동 시연은 ‘이전 사건으로 시연 전화’를 명시해야 한다. ‘시연 전화’ 확인창에서 선택 역할과 공통 등록번호를 확인한 뒤 실제 발신한다. 순수 연결 시험도 세 역할을 지원한다.

| API | 동작 |
| --- | --- |
| `GET /api/events/{id}/contact` | 저장된 판단·계획·전화 조회, AI 호출 없음 |
| `POST /api/events/{id}/contact` | 최초 추천 또는 역할/사유/시연 계획 저장, 전화 없음 |
| `POST /api/phone/calls` | plan ID·revision·request UUID·확인값으로 발신 |
| `POST /api/phone/test` | 선택 역할로 순수 연결 시험 |

발신 API는 임의 번호·모델·엔드포인트를 받지 않는다. Origin 검사, 엄격한 역할 enum, 최신 계획 revision 확인을 적용한다. 이전 사건을 시연하더라도 원래 사건 생성 시각을 보존하고 별도 발신 기준 시각을 기록한다.

## 전화 내용과 중복 처리

모든 통화의 첫 안내는 ChemiGuard AI 시연 전화이며 OpenAI로 음성을 처리한다는 내용이다. 현장 안전관리자에게는 미착용 부위나 보호복 불일치와 확인 요청을, 안전 관제실에는 누출 징후와 물질/실제 누출 미확인을 전달한다. 사내 119는 해당 역할의 시연이며 실제 긴급 신고가 아님을 안내한다. 초기 전달은 짧게 하고 상대 답을 기다린다. 주소·부상자·화학종·현장 조치를 추정하지 않는다.

- 같은 사건·역할·수신번호는 영속적으로 한 번만 접수한다.
- 사용자 최신 요청에 따라 등록번호 전체 50초 간격이다. 역할·개소가 달라도 같은 번호에는 50초 안에 다시 걸지 않는다. 이전 5분 간격/10분당 3회 제한을 대체했다. 실제 발신 접수 시각을 우선 사용하며 대기열에서 지연된 통화도 발신 직전에 간격을 확인한다.
- 발신 대기열 최대 4건과 단일 발신 worker로 같은 번호의 동시 통화를 막는다. 역할이 다른 사건은 접수 순서대로 처리한다. 일반 누출 우선 정렬은 없으며 마지막 시연의 통합 전화는 아래 후속 규칙을 적용한다.
- 발신 직전에 120초 신선도·검토 여부·근거 유효성을 재검사한다. 제한 사유와 전화 결과는 별도로 표시한다.
- 재시작·결과 불명 자동 재발신, 부재중 재시도, 추가 전화/착신 전환 도구는 없다.
- 음성/DTMF 수신 확인은 통화 이력에만 남고 사건 검토·경보 해제·현장 조치 완료로 바뀌지 않는다.

## 실제 확인과 한계

초기 연락 입력으로 실제 API 3건을 요청했을 때 역할은 모두 맞았지만 미착용·누출은 근거 재확인을 선택했다. 제품 전용 결과 형식과 부모 관찰 검사를 보강하고, 실제 누출 검출 근거 및 ‘사고 확정이 아니라 담당자 연락에 필요한 근거’라는 질문을 명확히 했다. 변경한 `contact-evidence-v2`로 세 종류를 각각 새로 호출해 역할·근거·사유가 모두 일치했다(621.5/318.7/285.1 ms). 기존 개발 사건의 연락 기능 확인이며 독립 모델 정확도 평가가 아니다. 이전 응답과 새 응답은 비공개 `.data/contact-routing-verification`에 함께 보존했다.

전화/연락 오프라인 검사 39개, 기존 Decisions 병렬 관련 4개 및 정책 migration 포함 8개, Node 20개가 통과했다. 브라우저에서 세 종류의 추천, 119 역할 변경 사유와 기존 번호 확인창을 확인했다. 검증용 역할 변경을 다시 관제실로 돌려놓고 실제 발신 버튼은 누르지 않았다. 명칭 정정 후에는 반복 API·통화 시험을 추가하지 않는다.

이번 구현으로 새 실제 전화는 걸지 않았다. 기존에 확인한 OpenAI Realtime 전화 연결을 재사용하며, 변경된 역할별 음성 문구의 실제 청취는 아직 별도로 확인하지 않았다. ClawOps 계정의 서버 녹음·자동 받아쓰기/요약 제공자 확인은 남아 있다. SDK 로컬 녹음 끄기와 계정 후처리 비활성을 혼동하지 않는다.

API 계약 근거: [OpenAI Decisions 가이드](https://developers.openai.com/api/docs/guides/decisions). 연락 규칙은 사용자 지정 정책이다.

## 후속 실제 수신 확인과 간격 변경

사용자 요청으로 기존 등록번호에 미착용→현장 안전관리자, 누출 의심→안전 관제실, 보호복 불일치→현장 안전관리자를 순차 발신했고 사용자가 세 안내 내용을 모두 정상 확인했다. 정상 통화는 각각 23/23/29초이며 모두 우리 gpt-realtime-2 세션과 통신사 정상 종료를 확인했다. 첫 미착용은 벨을 놓쳐 no-answer였고 사용자 명시 재시도 승인 후 다른 실제 저장 미착용 사건으로 재시험했다. 과거 사건/전화 이력을 덮어쓰지 않았다. 마지막 불일치 통화는 음성 수신 확인도 기록됐다.

이때 사용자가 50초 이하 영상 시연에 맞춰 5분 제한을 50초로 줄이도록 요청했다. 등록번호 전체의 50초 간격으로 구현했고 이전 10분당 3회 제한도 대체했다. 관련 경계·발신 지연·직렬 처리 3개 오프라인 검사와 빌드를 통과했다. 기존 자동 발신 꺼짐은 유지한다.

## 세 번째 영상의 매 시연 통합 전화

사용자 최신 요청은 한 번 예약을 소비한 뒤 끝내는 방식이 아니라 공개 페이지에서도 receiver를 새로 시연할 때마다 한 통을 안내하는 것이다. 로컬 `POST /api/phone/demo`의 enable/disable로 범위를 켜고 끈다. 기존 arm/cancel도 보존한다. `GET /api/phone`의 demo.per_run_enabled와 세 번째 영상 상단에 현재 설정을 표시한다.

설정 활성화 뒤 `POST /api/runs`로 새로 시작한 receiver 실행만 영속 예약을 생성한다. 페이지 열기/새로고침/시작 전 과거 사건/재시작 복구는 예약을 만들지 않는다. 다른 두 영상과 일반 사건 자동 전화는 여전히 대상이 아니다. 공개 프록시는 직접 번호 발신·전화 설정 API를 계속 차단하되, 사용자가 승인한 receiver 시연 시작은 통합 전화를 유발할 수 있다.

동일 실행의 미착용·누출 두 사건이 유효하고 각 실제 연락 Decisions가 정책과 일치해야 안전 관제실 역할의 한 통을 발신한다. 두 사건/Decisions ID·원래 시각을 보존하고 Realtime이 미착용 부위와 누출 징후를 모두 안내한다. 관찰 시점이 다를 수 있으며 같은 사람·인과관계·물질·실제 사고를 단정하지 않는다.

실행별 최대 한 통, 번호 공통 50초 간격, 단일 발신 worker와 사건 120초 신선도를 유지한다. 간격이 남으면 큐에서 기다리고 발신 직전 양쪽 근거·검토·generation을 다시 확인한다. 누락·오류·fallback·중지·탐색·재시작은 자동 재발신 근거가 아니다. 완료 기록을 삭제하거나 기존 통화를 다시 보내지 않는다.

첫 통합 시연은 실제 연락 Decisions HTTP200/sufficient 2건(254.1/292.3ms), gpt-realtime-2 음성 응답, 전화 completed로 확인했다. 매 실행 자동 예약 전환 후에는 추가 실제 전화를 시험 발신하지 않았다. 실제 청취 확인과 현장 조치 완료는 별도다.
